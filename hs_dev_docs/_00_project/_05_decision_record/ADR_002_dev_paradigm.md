# 架构决策记录 (ADR)：开发范式

- **编号**：ADR-002
- **状态**：ACCEPTED
- **日期**：2026-10-10
- **作者**：hardstone

---

## 1. 背景与问题阐述 (Context)

新产品 L 变更需在阶段 1～2 选定开发范式，避免默认上完整 DDD/微服务。产品为本地优先写作客户端，规则中等，集成点（AI、多 Sync）可变。

---

## 2. 备选方案权衡 (Options Considered)

| 方案 | 优势 | 劣势 |
|---|---|---|
| **A：模块化客户端 + 端口适配器（B2/B3 薄域 + F2）** | 适配器可测；小团队够用 | 需自律维持端口边界 |
| **B：完整 DDD + 多限界上下文** | 术语严密 | 对本产品过重，拖慢 MVP |
| **C：无分层单包** | 起步快 | Sync/AI/编辑器缠死，难测难换原生云 |

---

## 3. 决策结果 (Decision)

**拟采纳方案 A：**

| 维度 | 取值 |
|---|---|
| 产品规模 | 小 |
| 产品类型 | 写作工具客户端 |
| 后端/核心 | **B2 用例层 + 模块化**；对 AI/Sync 使用 **端口适配器（B3 局部）** |
| 前端 | **F2 按业务 Feature**（library / editor / ai / sync / settings） |
| 明确不选 | 完整 DDD（B5）、微服务、FSD 全套 |

---

## 4. 影响与后续行动 (Consequences)

- 阶段 2 架构文按 Feature + 端口绘制，不写假 BC。  
- 测试 seam 落在 `AiProvider`、`SyncProvider`、`DocumentStore`（工作目录文件）。  
- 原生云商业化 = 新适配器，不改编辑器核心。
